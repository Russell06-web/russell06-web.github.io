# 易用性測試指南（Usability Testing Guide）

本資料夾用於規劃、執行與記錄作品集主打案例的真人易用性測試。所有文件均為**可直接使用的空白範本**，尚未包含任何真實測試資料。

## 測試目的

驗證兩個主打案例（藝文票務管理後台、Volleyball Hub）在真實使用者操作下，是否能：

- 順利完成核心任務（找到退票申請、完成報名等）
- 正確理解介面上的關鍵提示（二次確認、程度篩選、報名／候補狀態）
- 在合理時間內、不需額外說明的情況下自行完成操作

測試結果將用於：(1) 驗證既有設計決策是否成立、(2) 找出實際存在的可用性問題、(3) 作為案例頁面「驗證」區塊的真實佐證，取代目前的自我檢核（self-review）說法。

## 建議受測人數

每個案例 **3–5 人**。人數不需要多，重點是能觀察到重複出現的問題模式（通常 3–5 人即可發現多數重大可用性問題）。

## 每次測試時間

**20–30 分鐘**，包含：

- 開場說明與取得同意（約 3 分鐘）
- 任務操作＋Think Aloud（約 15–20 分鐘）
- 簡短訪談與結束（約 5 分鐘）

## Think Aloud 操作方式

請受測者在操作過程中，將心裡想的話說出來，包括：

- 「我現在想找的是...」
- 「我不確定這個按鈕是做什麼的」
- 「我原本以為會...但結果是...」

主持人只需要在受測者長時間沉默時輕聲提醒：「可以說說你現在在想什麼嗎？」不需要引導答案。

## 主持人注意事項

- 保持中立語氣，不要用表情或語氣暗示「這樣做不對」或「你答對了」。
- 記錄客觀事實（點擊了哪裡、停留多久、說了什麼），不要在記錄當下加入自己的詮釋或設計建議——詮釋留到測試後統一整理。
- 每位受測者的任務、腳本用語都要一致，避免因說明方式不同而影響結果。
- 若受測者卡住超過 1–2 分鐘且明顯感到挫折，可以說「這邊我們就先跳過，繼續下一題」，不需要讓對方硬撐。

## 不誘導使用者的原則

- 不要說「你要不要點點看那個退票按鈕」，只能說「請完成任務一」。
- 不要在受測者操作前解釋介面邏輯或術語。
- 若受測者詢問「這是做什麼的？」，可回答「這題想請你自己判斷看看」，不要直接給答案。
- 任務描述使用受測者的語言（例如「找一筆需要處理的退票」），不要使用系統內部術語（例如避免直接講出畫面上的按鈕名稱）。

## 錄音、錄影或截圖前需取得同意

- 測試開始前，需口頭或書面告知受測者：測試目的、資料用途（僅用於作品集可用性驗證與研究）、是否錄音／錄影／截圖、資料是否會公開（若公開，僅使用匿名化的觀察紀錄，不使用可辨識個人身分的錄音錄影原始檔）。
- 受測者可隨時要求停止錄製或退出測試，不需要說明原因。
- 未取得明確同意前，不得開始錄製。

## 如何將觀察整理成設計修改

1. 測試結束後，將每位受測者的 `observation-template.csv` 記錄彙整到 `result-summary-template.md`。
2. 找出**重複出現在 2 位以上受測者身上**的問題（單一個人的個別狀況，優先程度較低）。
3. 依 Severity 排序，優先處理「造成任務失敗」或「造成明顯誤解」的問題。
4. 針對每個問題寫下具體的設計修改方向，並在修改後回到案例頁面的「Design Iterations」區塊記錄前後差異。
